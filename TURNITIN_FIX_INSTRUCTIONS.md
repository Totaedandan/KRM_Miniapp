# Turnitin перестал проверять файлы — фикс после редизайна UI (авг. 2026)

## Проблема

12 августа 2026 Turnitin выкатил новый интерфейс: страница логина переехала на
Angular SPA (`home.turnitin.com/sign-in`), а Feedback Studio частично
перешёл на новые веб-компоненты `tii-grn-*` вместо старых `tdl-*`. Из-за
этого автоматизация на Playwright (модуль вроде `turnitin_service.py`)
стала падать — либо сразу на логине, либо позже при загрузке файла.

Если у вас похожий Playwright-скрипт логинится на Turnitin и грузит файлы —
почти наверняка сломан по той же причине. Ниже — что именно проверить и
пофиксить, в порядке, в котором баги проявляются один за другим.

## Диагностика (как искать, если баг немного другой)

Не гадайте по логам — сделайте скриншот/дамп DOM прямо в момент падения:

1. Отдельным одноразовым скриптом (НЕ трогая живой процесс, чтобы не мешать
   друг другу — в частности, если в коде есть `pkill -f chrome-linux` при
   ошибке, он убьёт оба браузера) залогиньтесь реальными кредами, дойдите до
   места падения, снимите `page.screenshot(path=..., full_page=True)`.
2. Если баг в поиске кнопки — через `page.evaluate()` пройдитесь по всем
   `<button>` (включая shadow DOM: `if (el.shadowRoot) deepFind(el.shadowRoot)`)
   и распечатайте их `aria-label`, `class`, `data-px`, координаты `x,y`.
   Сравните с тем, что реально ищет ваш селектор.
3. Проверяйте на изолированном контейнере/окружении, а не параллельно с
   рабочей очередью — иначе сессии/куки конкурируют и результаты противоречивы.

## Баг №1 — логин зависает по таймауту

**Было:** заход на `/login_page.asp`, `sleep(2)`, затем клик по email-полю с
`timeout=8000`.

**Стало:** Turnitin теперь редиректит `/login_page.asp` на
`https://home.turnitin.com/sign-in` — новый Angular-компонент, который
рендерит реальные `<input>` только через ~6-9 секунд (грузит JS-бандлы).
Старых 2+8 секунд не хватает — падает по таймауту ещё на этапе редиректа.

**Фикс:**
- Заходите сразу на `https://home.turnitin.com/sign-in` (пропускает лишний
  редирект-хоп).
- Увеличьте timeout первого клика (по email-полю) до ~25000мс — Playwright
  сам поллит появление элемента, лишний sleep не нужен.
- Поля теперь `id="sign-in-email"` / `id="sign-in-password"`,
  `type="text"` (НЕ `type="email"`!) — добавьте эти id в селектор первым
  вариантом, старые варианты (`input[type="email"]`,
  `input[placeholder*="email" i]`) оставьте как fallback.

## Баг №2 — после сабмита формы код не дожидается ответа

**Было:** после клика Submit — `page.wait_for_load_state("domcontentloaded",
timeout=30000)`, потом `sleep(3)`, потом проверка `page.url`.

**Проблема:** новый sign-in — SPA. Сабмит формы шлёт XHR и делает
**клиентский** редирект после ответа сервера — обычной браузерной навигации
не происходит, `wait_for_load_state` тут бесполезен и возвращается сразу,
пока кнопка ещё крутит спиннер. Итог: код проверяет `page.url` слишком рано,
пока страница ещё "https://.../sign-in", и либо ошибочно думает, что логин
не удался, либо (если проверка не учитывала "sign-in") ошибочно считает
логин успешным, хотя это ещё старая страница.

**Фикс:** вместо fixed-wait — поллинг URL до ~20 секунд:
```python
for _ in range(40):
    await asyncio.sleep(0.5)
    if "sign-in" not in page.url:
        break
await asyncio.sleep(2)
if "login_page" in page.url or "sign-in" in page.url:
    raise TurnitinError("Неверный логин или пароль")
```
Важно: проверка ошибки логина теперь должна включать `"sign-in" in page.url`,
а не только старое `"login_page" in page.url`.

## Баг №3 — кнопка «три точки» (actions menu) не находится

**Было:** поиск кнопки по `aria-label.includes('Display actions menu')` ИЛИ
`data-px === 'more-options'`, плюс доп. фильтр `r.y > 300` (чтобы не спутать
с кнопками в шапке страницы).

**Проблема:** кнопка находится по атрибутам корректно, НО у нового, более
компактного дизайна она теперь рендерится на `y≈187-208` — старый порог
`y > 300` её отфильтровывает. Кнопка просто никогда "не находится", хотя
физически есть на странице.

**Фикс:** уберите фильтр по `y`, оставьте только проверку атрибутов —
`data-px === 'more-options'` и так уникален среди кнопок страницы:
```js
if (aria.includes('Display actions menu') || data === 'more-options') {
    const r = el.getBoundingClientRect();
    if (r.width > 0) return {x: ..., y: ...};  // убрали "&& r.y > 300"
}
```

## Баг №4 — кнопка Submit (после превью загрузки) не находится

**Было:** поиск кнопки по `el.className.includes('tdl-button-filled')`.

**Проблема:** Turnitin частично мигрировал компоненты с `tdl-button-*` на
новые `tii-grn-button-*` (та же дизайн-система, что и в остальном Feedback
Studio). Реальный класс кнопки теперь `tii-grn-button tii-grn-button-filled
size-medium`. Старые `tdl-*` кнопки местами ещё остались на той же странице
(миграция частичная) — поэтому проверяйте ОБА варианта, не просто замените
один на другой:
```js
if (el.tagName === 'BUTTON' &&
    (el.className.includes('tdl-button-filled') || el.className.includes('tii-grn-button-filled')) &&
    !el.disabled) { ... }
```

## После фикса — что дальше по цепочке обычно ОК

Всё, что идёт после Submit (ожидание % похожести/AI-детекта по тексту типа
`/^[0-9]+%$/`, клик по проценту, скачивание PDF, запрос удаления сабмишна) —
у нас проверялось и оказалось рабочим без изменений, эти части ищут по
текстовому содержимому (`%`), а не по CSS-классам, поэтому устойчивее к
подобным редизайнам. Если у вас там тоже всё сломано — скорее всего другая
причина, ищите отдельно тем же методом (скриншот + дамп кнопок в момент
падения).

## Как проверяли, что реально работает

Не полагались на код ревью — прогнали реальные застрявшие заказы (4 штуки,
с 12 августа) через живую очередь после фикса и убедились, что каждый дошёл
до конца: логин → загрузка файла → ожидание отчёта → скачивание PDF →
удаление сабмишна. Все 4 завершились успешно.
