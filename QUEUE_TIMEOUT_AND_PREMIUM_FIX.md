# Очередь Turnitin: таймаут на зависание + отдельный браузер для премиум

Оба фикса — только в одном файле: `bot/services/queue_manager.py`. Если у
второго бота этот файл не менялся отдельно от нашего — можно просто заменить
его целиком тем, что приложен ниже. Если менялся (например, свои тексты
сообщений) — накатите два коммита вручную, диффы описаны по шагам.

Коммиты в этом репозитории (для точной сверки):
- `3ea9841` — "Add hard timeout ceiling to Turnitin queue processing"
- `745e2f9` — "Give premium Turnitin orders an on-demand overflow browser"

## Проблема №1 — заказ завис на 17+ часов, встала вся очередь

Один заказ (#13, обычная очередь) завис в обработке: браузер Chromium был
жив и реально грузил CPU, но за 17+ часов — ни одной строки в логе, ни одной
ошибки, ни одного повтора. Где-то в Playwright-коде есть `await` без
собственного таймаута (скорее всего `frame.evaluate()` на LTI-фрейме,
который отсоединился/сломался — у него нет встроенного тайм-аута).

Критично: `_worker()` обрабатывает заказы **строго по одному**, ждёт
завершения текущего, прежде чем взять следующий. Значит один зависший заказ
блокирует ВСЮ очередь — и обычную, и премиум — сколько угодно долго. То, что
у премиум и обычной разные `class_id`/`assignment_id` в самом Turnitin, тут
не спасает — это разделение только на стороне Turnitin, а не в нашем воркере.

### Фикс: жёсткий потолок по времени

Добавлена константа и обёртка:

```python
PROCESS_TIMEOUT_SEC = 3600  # 60 минут — с запасом даже на полный цикл ретраев
...
sim_path, ai_path = await asyncio.wait_for(
    service.process(...),
    timeout=PROCESS_TIMEOUT_SEC,
)
```

Плюс отдельный `except asyncio.TimeoutError:` — у самой `TimeoutError()` нет
текста сообщения, поэтому текст ошибки формируется явно (`"Обработка
зависла (>60 мин) и была прервана"`), иначе `error_text` в базе был бы
пустым. Теперь любое зависание автоматически рвётся максимум через час,
заказ уходит в `error`, юзер получает уведомление, очередь освобождается.

## Проблема №2 — премиум реально не приоритетный

Даже без зависания: пока обрабатывается обычный заказ, премиум просто ждёт
своей очереди наравне с остальными — хотя по смыслу премиум (×1.5 к цене)
должен идти вперёд обычных, а не топтаться позади них.

### Фикс: overflow-браузер по требованию

Раньше `_worker()` был простым блокирующим циклом: взял заказ →
`await self._run_turnitin(job)` → ждёт → берёт следующий. Пока `await`
висит на текущем заказе, цикл вообще не может заметить, что подошёл
премиум-заказ.

Переделано на диспетчер с двумя "слотами":

- **Основной слот** — общий персистентный `turnitin_service` (как раньше),
  им пользуется любая очередь, когда он свободен.
- **Overflow-слот** — отдельный, свежесозданный `TurnitinService()` со
  своим собственным браузером. Поднимается **только** если премиум-заказ
  пришёл, пока основной уже занят обычным — тогда премиум не ждёт, а сразу
  уходит в свой отдельный браузер параллельно. Закрывается сразу после того
  как этот премиум-заказ обработан.

```python
async def _worker(self):
    while True:
        dispatched = False
        async with self._lock:
            active = await database.get_active_orders()
            for job in (o for o in active if o["status"] == "ready"):
                is_premium = bool(job.get("is_premium"))
                if self._main_busy_order is None:
                    self._main_busy_order = job["id"]
                    await database.update_order(job["id"], status="processing")
                    asyncio.create_task(self._run_turnitin(job, overflow=False))
                    dispatched = True
                    break
                if is_premium and self._overflow_busy_order is None:
                    self._overflow_busy_order = job["id"]
                    await database.update_order(job["id"], status="processing")
                    asyncio.create_task(self._run_turnitin(job, overflow=True))
                    dispatched = True
                    break
        if not dispatched:
            self._wakeup.clear()
            await self._wakeup.wait()
```

Заказы теперь выполняются как фоновые задачи (`create_task`), а не через
блокирующий `await` внутри цикла — поэтому диспетчер продолжает крутиться и
успевает заметить премиум, пока обычный ещё обрабатывается.

`_run_turnitin` получил параметр `overflow: bool`:

```python
async def _run_turnitin(self, order: dict, overflow: bool = False):
    from services.turnitin_service import turnitin_service, TurnitinService
    overflow_service = TurnitinService() if overflow else None
    service = overflow_service or turnitin_service
    ...
    try:
        sim_path, ai_path = await asyncio.wait_for(service.process(...), timeout=PROCESS_TIMEOUT_SEC)
        ...
    finally:
        if overflow_service is not None:
            await overflow_service.cleanup()   # закрыть временный браузер
            self._overflow_busy_order = None
        else:
            self._main_busy_order = None
        self._wakeup.set()
        await self._reevaluate()
```

**Важно про ресурсы**: overflow-браузер существует только пока реально есть
пересечение очередей — если премиум и обычная не накладываются друг на
друга по времени, второй Chromium вообще не запускается, расход RAM как
раньше. Два браузера одновременно — только в момент реального конфликта.
Актуально держать это в голове, если VPS с ограниченной памятью (у нас
2GB) — при активной одновременной нагрузке на оба слота потребление RAM
кратковременно удваивается.

## Как проверять после переноса

1. Заказать обычную проверку.
2. Как только в чате придёт «Начинаем проверку!» — **пока она ещё не
   завершилась**, заказать премиум.
3. В логах должна появиться строка `"премиум мимо очереди — отдельный
   overflow-браузер (основной занят заказом #...)"`.
4. Премиум должен получить отчёт, не дожидаясь завершения обычного.
5. Отдельно проверить сам таймаут — специально не нужно, он сработает сам
   при следующем реальном зависании (если оно случится) — просто убедитесь,
   что заказ через час автоматически уходит в `error`, а не висит вечно.
